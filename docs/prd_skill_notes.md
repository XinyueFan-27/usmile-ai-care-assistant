# PRD 写作经验记录（将来写“撰写 PRD”技能的素材）

> 用途：把写 usmile AI 护齿助手 PRD 过程中**确认有效**的做法记下来，PRD 定稿后据此写一个撰写 PRD 的技能（skill）。
> 记录规则：每条写清楚“做法 + 为什么 + 来源（哪次讨论 / 哪个决策）”。只记录已确认的做法；还在讨论的放到最后“待定”。
> 参考资料只记结构和思路，不抄原文：Product-Manager-Skills（deanpeters，CC BY-NC-SA 4.0）；林木《大模型产品模板：需求文档（PRD）》；一篇“用 Codex 写 PRD 如何协作”的文章（作者未注明）。

---

## 1. 读者与表述

1. **先定读者，再定写法。** PRD 的读者是没参与项目的研发、业务和管理层，不是作者自己。要求：不看背景也能读懂，并能找到自己关心的部分。（2026-10-16，Melody 提出，D28）
2. **开头放阅读指引。** 用一张表写清管理层、业务、研发分别重点看哪几章。（D28）
3. **删掉内部过程信息。** 不放版本讨论记录、决策编号、内部验收编号、文件路径、内部字段名、步骤编号、Demo 说明。这些放在内部文件里（如决策日志、评测对照表）。（D28）
4. **“分工表”改写成“依赖”。** 写清需要哪个团队提供什么、用于哪里。这比“谁负责什么”更符合 PRD 的用途。（D28）
5. **简单中文，术语第一次出现时解释，并附术语表。**（CLAUDE.md 工作方式；D28）

## 2. 证据与诚实

1. **问题陈述必须有证据。** 数字 + 用户原话，数字能追溯到统计结果。（prd-development 方法；步骤 ⑧）
2. **引号里只能是原文。** 原话用「」，不改写；编号放在隐藏注释 `<!-- R146 -->` 里，读者看到的是“京东评论”，脚本仍能逐条核对是不是原文子串。（铁律 8；D28）
3. **用脚本核对，并做反例测试。** 核对脚本要能报出“编造的话”和“没有编号的话”，否则不可信。（`src/check_quotes.py`；D27、D28）
4. **统一的不确定性标注。** 【假设目标】= 指标目标的设想；【业务假设】= 品牌方判断，数据里没有直接证据；【待核实】= 需查官方资料或平台规则。文档开头解释这三种标注。（步骤 ⑦–⑧）
5. **不编造任何内部数据。** 没有基准就写“先测基准”，不给虚假数字。（铁律 1）
6. **写明代价和反面证据。** 例如“只推荐自家产品”会让 11 条跨品牌提问答不了原意；周报的需求证据有正有反。（D25；概念卡）

## 3. 结构

1. **骨架用标准 PRD 顺序**：概述 → 背景与问题 → 目标与指标 → 用户 → 范围（含不做什么）→ 功能需求 → 后续版本 → 非功能需求 → 约束与依赖 → 风险 → 待决问题 → 附录。（prd-development；D28）
2. **每个功能统一四块**：用户故事 → 功能说明 → 业务规则 → 验收标准。（D28）
3. **验收标准用 Gherkin（假如 / 当 / 那么）**，每条只有一个“当”和一个“那么”，可以直接写成测试。（user-story 方法；步骤 ⑧）
4. **验收标准和评测题一一对应**，但对照表放内部文件，PRD 里只保留场景名称。（D27、D28）
5. **指标分阶段，每阶段有北极星、过程、护栏三类。** 护栏要包括“拒答过多”（误拒率），不只是“说错”。（概念卡；步骤 ⑧）
6. **风险按两类扫描**：产品本身（要不要 / 会不会用 / 能不能做 / 值不值）+ 外部环境（政策、经济、社会、技术、环境、法律）；每条标“上线前处理”或“持续跟踪”，上线前处理的条数要少。（derisk-measurement-advisor；步骤 ⑧）

## 4. AI 产品特有的设计原则

1. **能用规则的地方不用大模型。** 推荐型号由规则选，大模型只负责解释，这样不会编造型号和参数，结果可测试。（D25）
2. **大模型输出要有程序校验。** 例如理由里的数字必须能在官方参数里找到，否则换成模板句。（步骤 ⑧）
3. **先把边界写清楚**：不诊断、不推药、急症只提示就医、不处理售后、不评价竞品，并给出每种情况的处理方式。（铁律 6；步骤 ⑧）
4. **原型先做结构，官方信息用占位，不编造。**（D29）

## 5. AI 产品 PRD 的必备章节（2026-10-18 确认，参考林木模板，D30）

1. **为什么用大模型**：逐项比较人工、固定问答列表 / 关键词规则、传统机器学习、大模型，说清不可替代的地方；同时写明**哪些地方刻意不交给大模型**（选型号、高风险问题识别）。这是 AI PRD 和普通 PRD 最大的区别。
2. **产品目标分三层**：业务目标、用户目标、**模型目标**（正确率、出处率、拒答率、误拒率、延迟）。
3. **需求清单标 P0–P2**，需求分类里单列**数据需求**：埋点分用户操作链路和系统执行链路；明确什么算正例、什么算负例。
4. **两张图**：业务流程图（用户视角）+ 系统流程图（标出规则节点、大模型调用节点、工具调用节点、路由节点、人工介入节点和异常分支）；必要时加一张时序图给研发。
5. **模型选型**：先写约束（语言、成本、延迟、合规如数据不出境、接入方式），再列候选，结论写“当前选择 + 定稿条件”，没评测就标【待评测】，不假装已经选好。
6. **Prompt 设计**：按节点写角色、输出约束、核心指令、禁止事项；写版本管理规则（任何修改必须跑评测集）。完整 Prompt 放附录，验证后定稿。
7. **知识库代替训练数据**（不微调时）：来源、不收录什么、切分方式、每段必带信息、更新和审核机制。
8. **评测体系**：数据来源；覆盖度按真实提问比例分层，但**安全类按风险加权多放**；评分维度和权重，安全一票否决；单轮 / 多轮 × 正向 / 负向示例；触发重新评测的条件；负例回流和版本管理。
9. **效果保障**：输出质量控制、防编造（规则决策 + 只依据检索 + 出处和数字校验）、稳定性（重试 → 备用模型 → 兜底文案）、一致性。
10. **原型图章节**补 AI 特有交互：等待体验、结果不确定性（出处、免责）、反馈入口、可纠正。
11. **AI 能力边界**单列一章：能做到 / 做不到 / 已知缺陷。还没评测时，“能做到”要写成“设计目标，需评测验证”，不能写成“已验证”。
12. **数据飞轮**：反馈采集 → 监控告警（写清阈值和处理）→ 回流闭环；面向品牌方的洞察可以放在这里。
13. **上线与运营**：分阶段灰度（含上线前的小规模用户测试）和 AB 方案、成本监控、回滚的触发条件和步骤，以及“最坏情况下保留什么功能”。

## 6. 证据与竞品

1. **竞品分析可以先用手里已有的数据做**：比较各品牌用户主要卡在哪里、AI 能缓解的比例，结论只用来判断机会；样本小要写明，没调研的竞品功能标【待核实】。（2026-10-18，D30）
2. **内部追溯编号只放内部文件**：评测题编号（E-01 等）放在 eval 文件里，PRD 只写场景名称并说明“每个场景都有对应测试题”。（2026-10-18，D30）

## 7. 工作流（来自“用 Codex 写 PRD”文章，部分已采用）

- 已采用：流程图和时序图用 Mermaid 写在 Markdown 里（GitHub、Obsidian 都能直接显示；PlantUML 在 GitHub 上不显示）。写完要真的渲染一遍检查语法。（D30）
- 已采用：原型用截图嵌进 PRD（`<img width>` 控制大小），不另画 SVG。（D30）
- 已采用：改完 PRD 后，凡是引用了旧章节号的内部文件（评测对照、原型说明）一起更新。
- 经验：脚本核对抓到过一次编号写错（引文是对的，但标成了相邻的提问编号），说明核对必须每次跑，不能凭记忆。（2026-10-18）

- 文档用 Markdown 写在本地，作者和 AI 改同一个文件；确认后再发布到团队工具（如飞书文档）或导出 PDF。
- 文档要发给不用 Markdown 的人看，最后一步一定是转换成对方方便查看的形式。
